# Supplier Upload Portal (E1-008, E1-025D, E1-028)

The external supplier experience at `/upload/demo-construct-pro` and `/en/upload/demo-construct-pro` implements [canonical mockup 08](../design/mockups/08-supplier-upload-portal.png). It has its own brand-and-locale header, invitation context, requested-document list with shared requirement status/progress, security and help panels, decorative mountain treatment, and footer. Its header, main content, and footer share the centered 1350px low-level `PortalContainer` geometry and 32/24/16px responsive gutters, while retaining a separate supplier-facing shell. It does **not** use `PublicHeader`, the authenticated app shell, or a supplier account. The [Invite Vendor drawer](invite-vendor.md) displays a demo URL for this route and opens the local preview in a separate tab.

The route accepts a token-shaped segment, but only the deterministic `demo-construct-pro` fixture resolves; unknown values return 404. This is a lookup of presentation data, **not** token validation or access control. The token fixture supplies company/vendor IDs, requesting/supplier identities and help contacts, not a second document dataset. Rows come from the same VendorRequirements and uploaded-document records as Vendor Details. The initial Construct Pro dataset is reconciled with Global Documents: five requirements, three approved uploads, tax in review and optional ISO missing (3 of 5, 60%). Romanian copy follows the approved images; temporary ComplyHub branding is replaced with plain `DEBIRO`. English copy awaits product-owner review.

E1-025D uses [supplier-upload-portal-new.png](../design/mockups/supplier-upload-portal-new.png) for the supplier context and requested-document area only; the header, security/help panels, artwork, footer and overall shell remain unchanged. The context has two identities and no template metadata. `SupplierRequirementContext` / `SupplierRequirementList` share markup/styles with Requirements Preview. Catalog-backed rows use the existing catalog names, descriptions and immutable appearance rather than duplicate mappings; custom identities can carry template-owned appearance. Required/optional labels appear below identity, independently of `În review` (yellow), `Încărcat` (green) and `Lipsește` (red). Both uploaded and in-review examples include filenames and available upload metadata. Progress counts only supplier-status `uploaded` requirements, handles zero requests safely, and the compact empty state does not fabricate rows.

Only missing requirements offer the full upload CTA and helper. PDF/JPG/JPEG/PNG extension, supplied MIME and the 10 MB limit are checked locally; errors are associated with the field. A successful selection creates a new metadata-only document identity, associates it by stable requirement ID, and changes Missing → In Review with internal Needs Review. Pending and approved files show their current filename/date and have no upload CTA. Rejection removes the active file reference, retains the old upload as history and immediately restores Missing/upload; replacement creates a new identity, never overwriting the rejected record. Approval changes the supplier badge to Uploaded and counts it as completed, independently of internal expiry status. The existing readonly ellipsis remains unavailable. No bytes are retained, stored or sent. The local notice makes this limitation explicit. The appearance contract supersedes all-blue sample glyphs. The security statements reproduce canonical mockup copy; they do not describe an implemented secure upload service. Privacy/terms and uploaded-row action affordances remain inactive because their destinations/actions are not defined. The internal Preview banner is never shown here.

There is no real invitation issuance, signed-token validation, expiry/revocation enforcement, supplier authorization, private object storage, upload API, OCR/AI, notification, or email delivery. Local human-review outcomes now propagate through the shared E1 lifecycle. A future server boundary must validate scoped invitation capabilities before serving private supplier data or accepting uploads, then write files to authorized private storage and replace these fixtures/local states. The existing demo URL must never be treated as a production capability.
