# Supplier Upload Portal (E1-008, E1-025D)

The external supplier experience at `/upload/demo-construct-pro` and `/en/upload/demo-construct-pro` implements [canonical mockup 08](../design/mockups/08-supplier-upload-portal.png). It has its own brand-and-locale header, invitation context, requested-document list with fixture status/progress, security and help panels, decorative mountain treatment, and footer. Its header, main content, and footer share the centered 1350px low-level `PortalContainer` geometry and 32/24/16px responsive gutters, while retaining a separate supplier-facing shell. It does **not** use `PublicHeader`, the authenticated app shell, or a supplier account. The [Invite Vendor drawer](invite-vendor.md) displays a demo URL for this route and opens the local preview in a separate tab.

The route accepts a token-shaped segment, but only the deterministic `demo-construct-pro` fixture resolves; unknown values return 404. This is a lookup of presentation data, **not** token validation or access control. The requesting organization, supplier, documents, uploaded sample rows, and help contacts are typed fixture data. The initial progress derives from the two fixture-uploaded rows (2 of 4, 50%). Romanian copy follows the approved images; temporary ComplyHub branding is replaced with plain `DEBIRO`. English copy awaits product-owner review.

E1-025D uses [supplier-upload-portal-new.png](../design/mockups/supplier-upload-portal-new.png) for the supplier context and requested-document area only; the header, security/help panels, artwork, footer and overall shell remain unchanged. The context has two identities and no template metadata. `SupplierRequirementContext` / `SupplierRequirementList` share markup/styles with Requirements Preview. Catalog-backed rows use the existing catalog names, descriptions and immutable appearance rather than duplicate mappings; custom identities can carry template-owned appearance. Required/optional labels appear below identity, independently of `În review` (yellow), `Încărcat` (green) and `Lipsește` (red). Both uploaded and in-review examples include filenames and available upload metadata. Progress counts only fixture-uploaded documents, handles zero requests safely, and the compact empty state does not fabricate rows.

The pending/missing document controls still accept a browser-local PDF, JPG, JPEG, or PNG selection up to the mockup's 10 MB limit. The in-review row uses a compact upload affordance beside its file to preserve the existing local-selection behavior; missing rows retain the full upload CTA and helper. The interface associates type/size errors with the relevant input and shows the selected filename as **selected locally**, not a fourth operational status or an uploaded file. Selection leaves the original fixture status and uploaded-only progress unchanged, is lost on reload, and sends no network request. The sample uploaded rows remain display-only. The new mockup's sample optional missing row differs from the retained fixture states: the existing optional ISU example is uploaded, while liability is required/missing. The task's appearance contract also supersedes all-blue sample glyphs. The security statements reproduce canonical mockup copy; they do not describe an implemented secure upload service. Privacy/terms and uploaded-row action affordances remain inactive because their destinations/actions are not defined. The internal Preview banner is never shown here.

There is no real invitation issuance, signed-token validation, expiry/revocation enforcement, supplier authorization, private object storage, upload API, document review, OCR/AI, notification, or email delivery. A future server boundary must validate scoped invitation capabilities before serving private supplier data or accepting uploads, then write files to authorized private storage and replace these fixtures/local states. The existing demo URL must never be treated as a production capability.
