# Vendor Details (E1-005 / E1-027B)

The dynamic `/vendors/[vendorId]` and `/en/vendors/[vendorId]` routes implement [canonical mockup 05](../design/mockups/05-vendor-details.png) for the deterministic `construct-pro` fixture. E1-026A resolves all 24 listed fixture identities and [locally created vendors](add-vendor.md) through the same `VendorDetailsPage` and typed view model. Unknown non-local IDs return Next.js 404; a local ID lost after refresh shows a return-to-Vendors recovery state. Fixture identity/contact/date data remain samples; configured-vendor compliance/counts now project current owned requirements and active documents.

`VendorDetailsPage` reuses `AuthenticatedAppShell` and `AuthenticatedPageHeader`. The Vendors navigation remains active. The page includes the vendor breadcrumb, identity and registration metadata, compliance summary, invitation/add-document actions, known contact fields, four functional section tabs, document/status table, and closing mountain banner. Romanian visible labels and descriptions follow the mockups; English localization preserves their meaning pending review. The canonical images are unchanged.

The E1-005A responsive composition keeps the shared page header unchanged while arranging its vendor identity, the status card, and the existing actions in a feature-owned grid. The company icon stays beside the name as the identity moves between rows; CUI, registration, and an intrinsically sized category badge stay with it. The status/actions move below identity before intermediate-width collision, then occupy separate rows with stacked buttons in the reduced authenticated layout. Contact items retain their mockup order and flow through a balanced three-column, two-column, or single-column layout as space decreases; remaining items expand to fill their row, with separators following cell boundaries.

Breadcrumbs, Vendors List names and the context-menu Open Supplier action navigate client-side. Document search filters fixture and [locally created document rows](add-document.md). The [Invite Vendor drawer](invite-vendor.md) opens over the same page for every owned vendor; it remains a local simulation with no real email or token. `Adaugă document` opens the shared Add Document drawer for fixture and locally created vendors. E1-027A reuses the shared search/filter primitives for document rows; its immediate status filter uses only the existing valid, expiring, expired, missing and review states. Reset preserves the query, and the trigger count excludes search. Desktop popover and mobile Drawer behavior follow the [shared contract](../design/ui-foundation.md#authenticated-search-and-filters-e1-027a). E1-027 activates missing-row upload and requirement row menus through the [snapshot template application flow](vendor-requirements.md); locally created review-required rows retain their matching Review destination. The document table scrolls within a focusable region at narrow widths; no page-level horizontal overflow is intended. Generated visual captures are ignored comparison artifacts, not approved baselines.

Other seeded Details views initially reuse only known identity, category, CUI and optional contact name from the list. Absent contact fields are omitted (an entirely absent contact block shows a safe empty message); documents and notes are not invented. Without configured requirements vendors retain the Attention setup semantics, without fabricating requirements. Known records from Global Documents appear in Details and supply the same actual accepted/current file ratio used by the list; zero files project safely as 0/0. A neutral Inactive badge near identity reads the shared vendor lifecycle state and never disables Details or editing, or changes compliance. Reactivation preserves the same data.

E1-026B adds the secondary `Editează furnizor` action before Invite and the primary Add Document action. The header moves status/actions below identity before the three controls crowd the title; actions wrap within their region and retain the existing mobile stacking. Edit reuses the Add Vendor form and shared Drawer. All eleven metadata fields prefill from known values; absent values remain empty, including missing required fixture email, which must be provided before Save. The canonical Romanian fixture address supplies the locale-independent draft; unchanged fixture address translations are preserved, while an edited address is business data shown verbatim in either locale.

The draft is separate from committed state. Save is enabled only for valid, normalized changes and publishes one atomic update to the existing browser-memory vendor store by stable ID. Details, contact fields, Notes and list search/filter/sort update without refresh; the route, lifecycle, current compliance projection, expiry, documents and invitation preview stay associated with the same identity. Save closes the drawer and announces `Furnizor actualizat`. Cancel/X/Escape/backdrop close a clean draft immediately; dirty close reuses the Requirements unsaved-changes confirmation with Continue Editing/Discard. The shared confirmation makes the underlying drawer inert and owns keyboard focus; backdrop mousedown prevents stealing its initial focus. Discard does not save. No empty edit drawer is offered for missing vendors.

Seeded vendors belong to the Demo company; local records carry their creating company ID. CUI uniqueness is checked within that company, excluding the edited ID. Existing alternate-company operational-workspace recovery remains unchanged; this is not a new workspace implementation. Category and descriptive industry remain separate; E1-027 shows a relevance warning when the edited category changes, but Save does not assign/remove templates, requirements or uploads. Edits survive client navigation and locale switches, not refresh. No backend, persistence, permissions or new invitation/lifecycle behavior is added.

Created vendors display only submitted optional contact/registration data and any submitted note, initially with an empty document table and a setup-needed summary instead of a compliance claim. Local document creation may populate that table without fabricating valid status or compliance. Their supplier-portal preview remains unavailable: no demo token is fabricated, but contact-based invitation simulation works. The fixture can later be replaced by a real application/API provider without changing the screen contract. No authentication, backend, durable persistence, remote upload, invitation sending or provider integration is added. E1-028 adds local configured-vendor compliance projection only. The banner mountain treatment reuses existing approximate artwork where no exact source asset exists.

E1-027 adds the shared two-step template-application Drawer, source/required table columns, removable provenance chips, company custom document types, missing-requirement upload and explicit requirement/document removal. Configuration is company/vendor-owned and snapshot-based; template deletion/editing and category changes never silently propagate. E1-028 replaces configured-vendor compliance snapshots with the shared current requirement/document projection. See [vendor requirements](vendor-requirements.md) for the local lifecycle and canonical mockup 24.

## Contacts, Activity and Notes (E1-027B)

[Canonical mockup 25](../design/mockups/25-vendor-details-contacts-activity-notes.png) defines the three additional workspaces. Contacts and note threads live in the existing vendor store, keyed by company ID and stable vendor ID; selectors and mutations reject another company's vendor. Company switching unmounts the previous workspace. These records survive client navigation and locale changes, not reload.

`VendorContact` has stable identity, optional name/role/phone, email, primary status, company/vendor ownership and creation/update timestamps. Existing known vendor contact fields seed the primary record without invented missing values. Vendor form fields, list contact name and Details summary are synchronized compatibility projections of that primary contact. The shared Add/Edit Contact Drawer requires a trimmed name and valid email, rejects same-vendor duplicate emails case-insensitively, and preserves ID on edit. Exactly one contact is primary when contacts exist. Setting another primary updates the summary and Vendor Edit; only non-primary contacts can be deleted, with shared confirmation. The table scrolls internally on mobile. Existing icons replace reference avatar photographs because no approved photo assets are supplied.

Activity projects the complete vendor-ID-scoped Notifications/Audit fixtures and known document-upload dates, deduplicating matching events. The same company-owned `LocalAuditEvent` source feeds Vendor Activity and the Notifications audit journal/CSV. Successful local creation/edit, invitation simulation, upload, review confirmation, template application, lifecycle changes and requirement removal record events; invalid, canceled and repeated no-op lifecycle/application actions do not. E1-028 adds one confirmed/rejected review event per successful outcome from the same source, alongside local review outcome persistence and configured-vendor compliance projection. Unknown actors/times are not fabricated; date-only uploads display dates only. Events sort newest first, with 5/10/20-row pagination. Shared SearchInput/FilterPanel compose text, supported event types, 7/30-day periods and available actors; Reset preserves search and counts exclude it. Periods use the shared E1 fixture reference, consistent with Notifications filtering. Audit events do not create delivered notifications or alter unread counts.

Notes is a thread-list/plain-text-editor workspace, stacked at 767px and below. Each `VendorNoteThread` owns a title/content, stable ID, company/vendor IDs and timestamps. New threads remain unsaved drafts until a dirty, non-empty-title Save; successful Save clears dirty state. E1-027B1 keeps the thread-list header `+` as the sole empty-state creation action. New and existing titles use the same lightly bordered input with visible focus; creating a draft focuses and selects its default title. Save trims the title, rejects blank/whitespace-only titles and commits title/content atomically; title-only changes participate in the existing dirty-state protection. Existing Vendor form notes map to a stable general thread without overwriting other threads; clearing that legacy text empties its content, while only confirmed thread deletion removes its identity. Thread selection, another draft, tab changes, navigation, browser Back and company switches protect dirty edits using the shared Continue Editing/Discard confirmation; unload uses native browser protection. Navigation API traversal is canceled before route restoration; the older-browser fallback uses a temporary same-URL history guard, released before confirmed navigation or when clean. Delete confirms, selects the next/previous saved thread deterministically, and shows the compact empty state when none remain. Notes remain internal and are not exposed in the supplier portal.

E1-027B1 restores the compact blue Documents information banner with the current missing `VendorRequirement` count, independent of search, filters or template associations. Uploading or removing a missing requirement updates the localized singular/plural message immediately; zero missing requirements hides the banner. It contains only the information icon/message, without `Vezi cerințele aplicabile` or a replacement action. Shared immediate filters and plain-text Notes deliberately supersede the reference's Apply-filter/rich-text affordances. Authenticated geometry and template snapshots remain unchanged. E1-028 updates this banner on rejection/replacement and connects Supplier Portal to the same current requirements; product-owner visual approval remains pending.
