# Vendor Details (E1-005)

The dynamic `/vendors/[vendorId]` and `/en/vendors/[vendorId]` routes implement [canonical mockup 05](../design/mockups/05-vendor-details.png) for the deterministic `construct-pro` fixture. The route looks up a typed, presentation-only `VendorDetailsViewModel`; unknown IDs return Next.js 404. Its vendor identity and shell context come from the existing Vendors fixture. Dates, names, contact values, and counts are static mockup-style samples, not live compliance results or a domain schema.

`VendorDetailsPage` reuses `AuthenticatedAppShell` and `AuthenticatedPageHeader`. The Vendors navigation remains active. The page includes the vendor breadcrumb, identity and registration metadata, compliance summary, invitation/add-document actions, five contact fields, four visible section tabs, the five-row document/status table, missing-document notice, and closing mountain banner. Romanian visible labels and descriptions follow the mockup; English localization preserves their meaning pending review. The canonical image is unchanged.

The E1-005A responsive composition keeps the shared page header unchanged while arranging its vendor identity, the status card, and the existing actions in a feature-owned grid. The company icon stays beside the name as the identity moves between rows; CUI, registration, and an intrinsically sized category badge stay with it. The status/actions move below identity before intermediate-width collision, then occupy separate rows with stacked buttons in the reduced authenticated layout. Contact items retain their mockup order and flow through a balanced three-column, two-column, or single-column layout as space decreases; remaining items expand to fill their row, with separators following cell boundaries.

Breadcrumbs and the canonical Vendors List ellipsis affordance navigate client-side. Document search filters the fixture rows locally. The invitation action now opens the [E1-007 Invite Vendor drawer](invite-vendor.md) over this same page; it remains a local preview with no real email or token. The non-Documents tabs, add/upload-document, filter, document-row actions, and applicable-requirements action remain visibly present but inactive: their destinations or workflows have not been specified or implemented. The document table scrolls within a focusable region at narrow widths; no page-level horizontal overflow is intended. Generated visual captures are ignored comparison artifacts, not approved baselines.

The fixture can later be replaced by a real application/API provider without changing the screen contract. This task adds no authentication, backend, persistence, upload, invitation sending, compliance calculation, or provider integration. The banner mountain treatment reuses existing approximate artwork where no exact source asset exists.
