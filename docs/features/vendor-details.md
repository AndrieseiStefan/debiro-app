# Vendor Details (E1-005)

The dynamic `/vendors/[vendorId]` and `/en/vendors/[vendorId]` routes implement [canonical mockup 05](../design/mockups/05-vendor-details.png) for the deterministic `construct-pro` fixture. The route looks up a typed, presentation-only `VendorDetailsViewModel`; unknown IDs return Next.js 404. Its vendor identity and shell context come from the existing Vendors fixture. Dates, names, contact values, and counts are static mockup-style samples, not live compliance results or a domain schema.

`VendorDetailsPage` reuses `AuthenticatedAppShell` and `AuthenticatedPageHeader`. The Vendors navigation remains active. The page includes the vendor breadcrumb, identity and registration metadata, compliance summary, invitation/add-document actions, five contact fields, four visible section tabs, the five-row document/status table, missing-document notice, and closing mountain banner. Romanian visible labels and descriptions follow the mockup; English localization preserves their meaning pending review. The canonical image is unchanged.

Breadcrumbs and the canonical Vendors List ellipsis affordance navigate client-side. Document search filters the fixture rows locally. The non-Documents tabs, invitation, add/upload-document, filter, document-row actions, and applicable-requirements action remain visibly present but inactive: their destinations or workflows have not been specified or implemented. The document table scrolls within a focusable region at narrow widths; no page-level horizontal overflow is intended. Generated visual captures are ignored comparison artifacts, not approved baselines.

The fixture can later be replaced by a real application/API provider without changing the screen contract. This task adds no authentication, backend, persistence, upload, invitation sending, compliance calculation, or provider integration. The banner mountain treatment reuses existing approximate artwork where no exact source asset exists.
