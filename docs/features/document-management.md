Document names/types, not filenames, are the primary links. Current Needs Review records open the existing `/documents/[id]/review` flow; other records open the same `DocumentManagementDrawer` over either listing. ## Current versions and internal updates

E1-029F anchors the existing external document store (records, ID-keyed exact files, deleted IDs and subscriptions) and its associated VendorRequirement snapshots/current-upload references to the same browser realm via the minimal `browserSession` helper. Previously these were module-local initializers: ordinary client navigation could retain them, but client module reinitialization reconstructed fixtures and lost runtime records/files/references. The regression test reproduces that boundary and verifies independent module consumers reuse the same objects after reinitialization. Documents, Vendor Details, Details/History/Replace, Review, Supplier Portal and current projections continue consuming their existing shared selectors; no screen-specific mutable copies or new version model exist.

Closing/reopening, route/component remounts, repeated SPA section navigation and company switch/return preserve versions and exact bytes. Ownership stays company/vendor-scoped and guarded at the same boundaries. Only document state and its requirement references adopt this lifetime; no broad application-state rewrite occurs. Reload, another tab or a new browser session starts fresh fixtures. No localStorage/sessionStorage/serialization/backend persistence is used. Server initialization never publishes browser state into a process-global registry. Version numbering, renewal/review/compliance/expiry/permission/audit semantics are unchanged.

Initial records without seeded history implicitly have version 1 and a version group equal to their ID. E1-029C's existing Construct Pro ISU fixture has approved current v2 and superseded v1 for two-entry preview/timeline validation; see [fixture data](../project/fixture-data.md). Later versions carry `versionGroupId`, ordered `version`, `previousDocumentId` and a distinct ID. Successful internal replacement sets `supersededById` on the old record without overwriting its file, metadata or review outcome. The new file becomes current; a configured VendorRequirement atomically references it with supplier-facing Uploaded. Unassociated documents remain unassociated; renewal does not fabricate a requirement.

The internal transaction validates the active membership, company/vendor ownership, current identity/reference, PDF/JPG/JPEG/PNG and 10 MB rules, real supplied DD.MM.YYYY dates and chronology. Number, dates, issuer and notes are optional, matching Add Document semantics. It derives Valid/Expiring Soon/Expired with the existing warning period and fixture clock, never Needs Review solely for an internal update. `updateSource=internal` distinguishes acceptance without review from human-reviewed documents; no reviewer metadata or authoritative verification is fabricated. One `document_replaced` audit event records actor ID/name, company/vendor/requirement IDs, previous/new IDs and versions, timestamp and localized action. Vendor Activity and Notifications/Audit reuse that event, without creating delivered/unread notifications.

`activeDocuments` excludes both superseded and rejected records. Global/Vendor rows, counters, search/filter/sort, vendor compliance/completion/next expiry, Dashboard and Notifications projections consume current records only. Configured-requirement compliance rules and zero-requirement Compliant behavior are unchanged. Historical records keep their original outcome/status and never satisfy the current requirement. Superseded pending files cannot be reviewed through stale URLs.

Supplier upload remains Missing → In Review and document Needs Review. Rejection retains the upload and clears the current requirement reference. A subsequent supplier upload joins that requirement's version chain with a new ID and still requires approval. Initial Add Document review/extraction semantics are unchanged. Neither path parses arbitrary file contents or performs OCR/AI.

## Access and file limits

Existing active company memberships provide local E1 checks: Administrator can replace/renew and review; Reviewer can review; Viewer can read but cannot replace/renew or review. The existing role contract does not grant Reviewer document-management permissions. Details/history/download selectors and mutation boundaries reject foreign companies, inaccessible vendors, stale/current-reference mismatches and inactive memberships. These browser checks are not server authentication or authorization.

E1-029E keeps each version's actual File/Blob in the existing private tab-memory map keyed by its stable document/version ID, separate from serializable metadata. Creation records filename, MIME type and size from the actual supplied File. Internal renewal adds a new key and never overwrites or deletes the previous file; supplier rejection/re-upload also retains the exact submitted bytes. Identical filenames do not share a file reference. Current and historical downloads resolve only the selected version and preserve its filename. Active membership, company ownership and vendor relationship are rechecked at file lookup and download; Viewer/Reviewer/Administrator keep their existing view/download access. Object URLs are created only at the browser download boundary and revoked afterward, not stored in domain records.

Every seeded document record now starts with its own small valid demo PDF, explicitly labeled `DEBIRO demo fixture - no legal validity` inside the file and containing its stable version ID/number. This includes vendor-only documents and the two ISU versions: current v2 keeps `Autorizatie_ISU.pdf`; historical v1 uses `Autorizatie_ISU_v1.pdf`. MIME type and size reflect the actual files, not another version. These are test/demo artifacts, not vendor-submitted evidence. Renewing any seeded current document retains that exact original PDF. Missing versions, files, foreign/inactive access or stale browser references never start a substitute/fake download or regenerate a lost local file. Details disables known-unavailable Download with its existing subdued explanation; History omits known-unavailable downloads. A failed attempt shows the existing localized session-unavailable feedback without exposing storage paths. Reload restores only seeded files; local records/files are lost on refresh or in another tab. No API, remote upload, durable/private object storage, real PDF viewer, scanning or backend audit is introduced.

Known existing limitation observed during E1-029E validation: directly loading a drawer query URL can return HTTP 500 during SSR because the shared Drawer portal reads `document.body`; the drawer then renders on the client. Client-navigation opening is unaffected. Shared Drawer mechanics are unchanged in this file-retention task.
