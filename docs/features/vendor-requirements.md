# Vendor Requirement Templates (E1-027)

Vendor Details → Documents follows [canonical mockup 24](../design/mockups/24-vendor-requirement-template-assignment.png). `Setează documente din șablon` opens the shared Drawer: search company-owned templates, select one or more matching the vendor's operational category, inspect the union's new/existing document summary, then explicitly confirm. Incompatible templates are disabled. Cancel/Back/close create no requirements. No compatible templates gives a safe Requirements link. RO/EN use the same identities and state.

`VendorRequirement` is a company/vendor-owned snapshot: exactly one catalog ID or company-custom type ID, localized name/description, issuer, icon/color, required/optional flag, expiry warning, validity, upload status/reference, creation time, and source template IDs/name snapshots. Applying merges by the shared `documentIdentityKey`, not labels. Existing rules, metadata and uploads win; a new overlapping requirement uses the first selected template's rules. Every contributing template is recorded. Reapplication cannot duplicate a requirement or applied-template association. There is no live synchronization, automatic assignment, or propagation after template/category edits.

`VendorAppliedTemplate` is separate provenance with application time and a name snapshot. Confirmed chip removal removes only this association; requirements, uploads, statuses and requirement source IDs remain unchanged. Renaming/deleting a source template also leaves vendor snapshots/history intact. The Documents table combines uploaded and missing requirements, with source and required columns. Missing rows show no invented upload/date values. Their Upload action reuses Add Document with the snapshotted type preselected and locked. General Add Document offers the global catalog, reusable active-company custom types and the existing legacy manual types. A matching missing requirement receives the local upload without creating another row. An existing uploaded requirement is never overwritten by another manual upload.

Each requirement has a row-menu removal action and shared confirmation. An empty requirement removes only itself. An uploaded requirement explicitly warns that both requirement and associated local document will be deleted; confirmation removes both. Seeded document references are suppressed from Documents and Review for the same browser-memory session, without modifying fixture files. No file bytes or real storage are deleted because none are retained.

Saved template custom documents resolve to `CompanyDocumentType` IDs using existing accent/case/whitespace normalization. Same-company identical names reuse one type; other companies never share these IDs. Resolution happens only on successful template Save, alongside the existing independent global pending `CatalogCandidate` learning. Custom types remain reusable if their source template is deleted, and are never auto-published to the global catalog. Template-specific metadata/appearance and vendor snapshots remain independent of this reusable type definition.

Edit Vendor shows the approved relevance warning whenever its draft category differs from the committed value. Save preserves all existing configuration; industry never drives matching. Company/vendor ownership is checked at mutation boundaries and active-company selectors filter their sources. The existing alternate-company operational-workspace recovery remains in place rather than inventing a new workspace.

The Construct Pro five-row fixture is mapped to stable catalog identities (`insurance` → `liability`) and shared document records. Global Documents is the initial source for the overlapping tax/registration/ISU files; the vendor-only liability record stays outside the initial Global Documents dataset. This reconciles previously conflicting sample statuses/counts without changing mockups. Other vendors receive no invented requirements; known global documents may also appear in their Details. E1-028 derives configured-vendor compliance from current required requirements and their active files; unconfigured fixtures retain their existing snapshots. All mutations are tab-local browser-memory only and reset on refresh. Client navigation shares them; another tab is an independent demo session. No backend, API, persistence, OCR, authz, delivery, audit storage or synchronization is added.

The dense eight-column table scrolls within its existing focusable region at reduced available widths; drawers/modals reflow and keep internal scrolling at 320px. Shared Drawer/confirmation focus, Escape, inert background and focus-return mechanics are reused. Captures are ignored review artifacts, not approved baselines. English translation and final visual approval remain pending product-owner review.

## Shared review lifecycle (E1-028)

Supplier requirement status is only `missing` / `in_review` / `uploaded`. Internal document compliance is separately `needs_review` / `valid` / `expiring_soon` / `expired`; existing UI aliases `review`/`expiring` map from that domain. Review outcome is separately `pending` / `approved` / `rejected`, never a fourth supplier badge. Upload association uses stable company/vendor/requirement/type IDs, with at most one active document reference per requirement.

Confirm persists trimmed confirmed metadata, actor/time and an approved outcome; extracted metadata remains unchanged. It retains the active association, changes the supplier status to Uploaded and derives expiry compliance using the requirement's snapshotted warning days (existing 30-day default if absent). UTC calendar days are used: before today is Expired; today through the warning boundary is Expiring Soon; later/no expiry is Valid. Fixture initial compliance values stay deterministic until reviewed, not silently recalculated by a renewal job.

Reject requires the shared confirmation dialog. It retains the record and its requirement provenance, records reviewer/time, clears the active reference and restores Missing. Rejected records are excluded from current document rows, Needs Review, completion and compliance; replacement creates a new identity. Outcomes publish coherent document/requirement state before notifying projections and record one event in the existing LocalAuditEvent source. Repeated, foreign, missing or stale actions cannot resolve twice or create duplicate events. Full version/history UI is not introduced.

Configured vendors use the existing three compliance categories: a required missing/expired file is Noncompliant; required pending/expiring files need Attention; otherwise required files are Compliant. Optional requirements do not downgrade compliance. No required configuration gives Attention, and no requirements retains the existing setup/fixture handling. Valid counts include accepted Valid/Expiring Soon current files, never pending/rejected history. Vendor Details and Vendors List use the same projection. Dashboard and historical operational notification fixtures remain separate demo snapshots; their broader integration is outside this review lifecycle.

Supplier Portal and read-only Template Preview reuse SupplierRequirementList badges and the same uploaded-only progress calculation. Portal reads actual scoped vendor requirements; Template Preview remains illustrative and is never bound to unrelated reviewed vendors. E1 state is tab-local and not durable: normal client/locale navigation shares it; reload or a separately opened preview tab starts an independent fixture session. No storage, backend, authz, OCR, delivery or authoritative verification is added.
