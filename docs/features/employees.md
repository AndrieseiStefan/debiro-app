# Employee Management and Documents (E1C-005–006)

## Scope and shared presentation

`/company/employees` and `/en/company/employees` replace Coming Soon. Existing Company sidebar routes, dimensions, disclosures, active state and Company-rooted breadcrumbs are unchanged. The list composes shared PageHeader/primary action, document-density SummaryMetricCard, SearchInput, compact SelectField, DataTable styling, Avatar, StatusBadge, RowActionMenu, Button, Tooltip and Pagination. Pagination optionally accepts localized noun labels; existing document consumers retain their defaults.

The supplied mockup filenames are reversed: `employee-details.png` depicts the list, while `employees-list.png` depicts full Details. The pictured screens and `employee-create-drawer.png` define the composition; originals are preserved. Runtime employee/document values replace sample data. Explicit requirements supersede mandatory department/restrictive job-title selection, add the Source column and visible template action, use singular Add Document, and exclude employee sharing. Shared typography/control geometry is reused, not recreated.

Total Employees includes inactive records. Document progress, next deadline and tracking now derive from each owned employee workspace. Attention counts distinct active employees; Expiring Soon counts current expiring document requirements for active employees. Inactive employees retain all documentation but are excluded from these rollups. Tracking remains separate from employment Active/Inactive. Personnel-document metrics are restricted to Administrators; other members see unavailable values without private metadata. List-level bulk employee actions/reminder delivery remain unavailable; real document downloads are available inside authorized Employee Details.

## Domain, state and authorization

`Employee`: stable ID, mandatory company ID, first/last name, company-unique email, optional phone, free-text job title, optional department ID, ISO hire date, employment status, creation/update timestamps. Creating one never creates a user or membership. Job title is not an application role.

`Department`: stable ID, mandatory company ID, name, creation/update timestamps. There is no global department catalog. Names retain original display formatting.

Names are trimmed/required/1–80 characters; job title is required/1–100. Email must be valid, at most 254 characters and case-insensitively unique inside the company; another company may use the same email. Optional phone accepts international/free-form text up to 32 characters. Hire date must be a real ISO calendar date. The UI reuses the established `DD.MM.YYYY` Field/parser, not a new date picker. New department names are trimmed/1–80 and case-insensitively unique per company.

`debiro.employees-session` uses the existing company-keyed `browserSession` convention. Client navigation, locale changes, module reinitialization and switch/return preserve tab-memory records. Reload/new tabs restore fixtures; this is not backend/durable persistence. Only Demo Company has eight deterministic fictional employees and owned departments. Other/new companies start empty. Optional employee document workspaces, activity and company→employee→version Blob maps extend old sessions without resetting existing records. No employee file, requirement or historical activity is seeded. Existing company/vendor/template/document/sharing/review/compliance state is not reset or migrated.

Reads require active current-user membership in the active company. Writes require the existing Administrator company-management permission, not a generic document permission. Operations recheck access and record/department ownership. Reviewer/Viewer membership does not grant employee management. Foreign/stale IDs disclose no employee data. Malformed workspaces show a recoverable unavailable state without repair/overwrite. These E1 client checks are not a production authorization boundary.

`employees-state` owns list/get/create/update/status operations and department reads. Inline department creation is inside the employee save transaction, not an independent UI mutation: failed validation/save publishes neither record. A case-equivalent department created since opening is reused at save time. Editing preserves employee ID, company, creation timestamp and future extra associations. Inactive employees remain available/editable; there is no hard delete or reminder delivery.

## Employee document contracts

Employee requirements extend the existing Company document requirement contract with `employeeId`, a document-type identity snapshot and ordered `sourceTemplateIds`. Versions extend the existing document record with mandatory employee/requirement ownership and a monotonic version number. Each requirement has one nullable current pointer. All reads/mutations/files validate the active company, Administrator membership, owned employee, requirement and version. Reviewer/Viewer membership does not grant document metadata, preview, downloads, upload, review, history or activity. Client-side E1 checks are not a production security boundary.

The Company document lifecycle is extracted unchanged into `createOwnedDocumentEngine`, with Company and Employee ownership/storage adapters. The Company facade retains its operation names, policies, timestamps and template matching. Employee operations reuse the same validation, review, replacement, metadata editing, manual expiry, history, real-file downloader and status/date functions. Employee records/events use actual operation timestamps; compliance dates use the existing centralized E1 reference clock, not a separate employee clock. Vendor review/compliance rules are untouched.

The visible **Setează documente din șablon / Set Documents from Template** action uses the shared template Drawer/picker with an employee-only preview. Only owned Employee-scoped templates and document types are accepted; Vendor/Company definitions cannot be applied. Applying creates requirements, never files or uploads, and requires no vendor category. Existing document identity matching prevents duplicate requirements across repeated/overlapping templates. Applying another source preserves configured requiredness, warning thresholds, current file and history; ordered source links feed shared `TemplateSourceLabels`, accent resolution and row tint. Manual/unavailable provenance remains neutral. This does not change Company single-source or Vendor association/removal behavior.

Standalone Add Document reuses `CompanyUploadDrawer` through the employee adapter: required name/type/real file, optional issuer/expiry, optional requirement by default. Uploading a missing requirement binds its identity read-only without a second selector, mandatory checkbox or duplicate row. Shared PDF/JPG/JPEG/PNG, 10 MiB, non-empty-file and valid calendar-date checks apply. Original bytes remain private tab-memory Blobs; no artificial preview or fallback download is generated. Unsupported native PDF rendering offers the existing truthful fallback/download state. Employee files are never included in Company Document Sharing.

Uploads/replacements enter Needs Review. Human confirmation is not AI verification. Rejection requires a reason, removes the current pointer and preserves that rejected version/file in newest-first history. Replacement allocates the next version, retains older bytes/review decisions and makes only the new version current. Metadata changes retain version/upload identity but require review again. Manual expiration stores the existing separate override, without changing the original expiry date, bytes, ownership or historical versions. No hard deletion exists. Stale/foreign/corrupt state and failed saves do not publish partial metadata/files/activity; recoverable form errors retain entries. Company switching redirects to Dashboard and clears transient selections/drawers while preserving owned records.

## Status, KPIs and activity

All tracking is requirement/current-document based, never a file-count compliance heuristic:

- Zero requirements → **Nesetat / Not Configured**, not complete and not `0/0`.
- At least one requirement and every required requirement valid → Complete.
- Any required requirement missing, pending review, expiring soon or expired → Attention.
- Missing optional requirements do not block completion. Optional rows still contribute truthful document/expiry counts.

Details KPIs count distinct configured requirements, valid current documents, expiring current documents and missing required requirements. Historical/superseded/rejected versions do not inflate counts. List progress counts current uploads/configured requirements; next deadline uses current-document expiry only. Employment filters/sorting remain employment-based. The table reuses shared search/filter/sort, local responsive horizontal scrolling and pagination; selection downloads actual current files only, with no employee sharing or reminder UI.

Activity contains only successful employee create/edit, template association, upload, review, replacement, metadata and manual-expiration events. Each has a stable ID, company/employee IDs, actual timestamp and current actor identity; no fabricated fixture history. Reapplying an already associated template creates no fake event. Reads are Administrator/owner guarded, localized and newest first, with an honest empty state.

## Deferred integration boundary

Employee Dashboard/Notifications/Global Search integration and active reminder delivery remain subsequent E1C work. Templates are never automatically assigned. No payroll, leave, self-service, medical diagnosis/history/laboratory fields or full HR functionality is introduced. Use synthetic administrative documents in this E1 demo; do not log file contents or assume employers may collect arbitrary medical records. Fitness-for-work tracking is limited to authorized administrative compliance/expiry information. E2 needs explicit personnel access controls, lawful-purpose/data-minimization decisions, retention/deletion policy and private authorized file storage before production use; E1 establishes no production retention policy.

Future E2 endpoints (documentation only): `GET/POST /employees`, `GET/PATCH /employees/:id`, `GET/POST /departments`. Server-side authenticated company resolution must authorize personnel access separately from generally shared company documents, enforce ownership/uniqueness and commit employee/department creation atomically. Errors: invalid data 400, unauthenticated 401, forbidden 403, absent/inaccessible employee/department 404, duplicate/conflicting state 409. No HTTP endpoints are implemented here.

Document contracts reserved for E2 only: `GET/POST /employees/:id/documents`, `GET /employees/:id/documents/:documentId`, `POST /employees/:id/documents/:documentId/versions`, `POST /employees/:id/documents/:documentId/review`, `POST /employees/:id/documents/:documentId/expire`, `GET /employees/:id/documents/:documentId/history`, `POST /employees/:id/templates/apply`, `GET /employees/:id/activity`. Server-side authorization must verify personnel permission plus company, employee, requirement and version ownership on every operation, including file bytes. Additional errors: 413 oversized upload, 415 unsupported type; existing 400/401/403/404/409 classes also apply. No new HTTP APIs are implemented in E1.
