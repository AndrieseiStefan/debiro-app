# Documentation Policy

## Core rule

Do not create speculative detailed documentation. Create or update documentation only when a requirement becomes current, behavior becomes implemented/current, or a durable decision becomes accepted.

## Routing

- New feature → create or update the relevant `docs/features/<feature>.md` in its defining/implementation task.
- Architecture decision → update architecture documentation and add an ADR where appropriate.
- Security or data-ownership decision → update the relevant architecture documentation.
- Reusable visual rule → update design documentation.
- Mockup deviation → update relevant feature/design documentation and report it in the task outcome.
- Task completion → update current status and roadmap where relevant.
- Future idea only → keep it to a concise roadmap entry.

Documentation must describe current truth, not planned behavior as though it exists. Relevant stale documentation means the task is incomplete.
