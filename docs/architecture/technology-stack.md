# Technology Stack

**Status:** [ADR-0002](../decisions/0002-application-architecture-and-stack.md) accepted the base stack; [ADR-0003](../decisions/0003-cost-and-auth-architecture-review.md) changed authentication to Clerk identity/session only. Nothing is installed or implemented. Research checked 2026-09-23 against linked official sources. TASK-003 should pin compatible released versions when it creates the application.

## Selected choices

| Concern | Decision and reason |
| --- | --- |
| Language/runtime | TypeScript in strict mode on Node.js 24 LTS for web and worker; one runtime reduces solo-developer context switching. Node 24 is the LTS line as of research date ([Node releases](https://nodejs.org/en/about/previous-releases)). |
| Frontend | Next.js App Router with React, server rendering for public and protected entry pages, client components for the mockup interactions. It supports a Node server deployment ([Next.js deployment](https://nextjs.org/docs/app/getting-started/deploying)). |
| Styling | CSS Modules and CSS custom properties for mockup-matched tokens; accessible headless primitives only where an interaction needs them. No preset design system may override approved mockups. |
| Backend | One modular monolith in the Next.js Node process plus a separate worker command from the same codebase. No microservices. |
| API/application boundary | Same-origin JSON route handlers for browser calls; TypeScript view/application contracts and Zod runtime validation; server rendering may call application services directly. Central service-level authorization. No feature endpoints defined yet. |
| Primary database | PostgreSQL on Neon Launch, Frankfurt region, with pooled runtime connections and direct administrative/migration connections. Local database in Docker. Free Neon is for development only; production uses paid Launch for restore and capacity ([Neon pricing](https://neon.com/pricing), [pooling](https://neon.com/docs/connect/connection-pooling)). |
| Database access/migrations | Drizzle ORM on `node-postgres`, reviewed generated SQL migrations via Drizzle Kit. Run migrations once in deployment with a direct connection; never at every web instance startup or via production schema push ([Drizzle migrate](https://orm.drizzle.team/docs/drizzle-kit-migrate)). |
| Authentication | Clerk Hobby for verified email/password, recovery and managed sessions through its Next.js SDK. Clerk supplies identity/session only; a verified external subject maps to a minimal debiro user. Hobby is free at modeled internal-user counts, but has fixed seven-day sessions, no MFA and no custom Clerk-delivered email templates. Debiro must deliver Romanian/English verification and recovery email via signed Clerk `email.created` webhook and Resend, validating the Hobby flow before launch. Clerk stores identity data in the US, so production transfer/DPA review is required ([pricing](https://clerk.com/pricing), [email delivery](https://clerk.com/docs/guides/development/troubleshooting/email-deliverability), [security/data](https://clerk.com/security)). |
| Authorization/tenancy | Debiro-owned users, organizations, memberships, and roles in PostgreSQL; organization-scoped application/repository access plus PostgreSQL RLS on tenant tables. Clerk Organizations are not used for business tenancy. Supplier links are independently scoped capabilities. |
| Object storage | Private Cloudflare R2 Standard buckets with EU jurisdiction, through S3-compatible SDK; no PostgreSQL document blobs ([R2 location](https://developers.cloudflare.com/r2/reference/data-location/)). |
| Upload | Short-lived presigned PUT into untrusted staging, server-side finalize/check, scan, then promote to a separate final private key; authorized short-lived GET for clean files only ([R2 signing](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)). |
| Background jobs | `pg-boss` on the same PostgreSQL. Enqueue atomically with domain writes, retry/backoff/dead-letter, idempotent handlers; finite batch worker process. No continuous polling/supervision/listener in the web process; verify finite maintenance/retry behavior when pinning the library. No Redis in MVP ([pg-boss options](https://github.com/timgit/pg-boss/blob/master/docs/api/constructor.md)). |
| Scheduler | Railway cron drains jobs every 10 minutes and runs daily scheduled evaluation/cleanup commands; commands enqueue work idempotently. No always-on scheduler or dedicated Redis. Reassess latency/backlog before a continuous worker ([Railway cron](https://docs.railway.com/cron-jobs)). |
| Native text | Poppler `pdftotext` for eligible PDFs; bounded extraction and quality threshold. Images do not have native text. |
| OCR | Tesseract with `ron` and `eng` language data, only when native text is insufficient; runs in the EU worker. No paid OCR service in MVP ([Romanian language data](https://github.com/tesseract-ocr/tessdata/blob/main/ron.traineddata)). |
| AI structured extraction | OpenAI `gpt-5-mini` text input with Structured Outputs, behind a narrow provider adapter, plus runtime validation and human confirmation. Real document calls require the EU residency gate described in [security and data](security-and-data.md) ([model](https://developers.openai.com/api/docs/models/gpt-5-mini), [structured output](https://developers.openai.com/api/docs/guides/structured-outputs)). |
| Transactional email | Resend API with authenticated `debiro.ro` sending domain; use EU sending region where available. Templates/subjects are localized; sending is queued and idempotent. Resend states customer data, including message content and logs, is stored in the US; production use requires transfer/DPA review or a provider change ([pricing](https://resend.com/pricing), [GDPR/region](https://resend.com/security/gdpr)). |
| Localization | `next-intl` with Romanian (`ro`) canonical source catalog and reviewed English (`en`) catalog; ICU pluralization, dates/numbers/currencies, validation and email messages. Locale selection uses user preference/cookie and request context; exact route contracts are deferred ([next-intl](https://next-intl.dev/docs/getting-started/app-router)). |
| Hosting | Railway Hobby account already paid, EU West Amsterdam region; one always-on Next.js service and separate finite cron services from one repository. Neon and R2 remain external. Existing plan's included credit is shared account-wide ([Railway pricing](https://railway.com/pricing), [regions](https://docs.railway.com/deployments/regions)). |
| Environments | Local and production. Ephemeral preview deployments only when needed; no permanently running staging environment for MVP. Local PostgreSQL uses Docker; fixture UI does not require cloud accounts. |
| Observability | JSON logs with redaction and correlation IDs to Railway, Railway service metrics/alerts/health checks, Neon metrics, persistent pg-boss failure/backlog checks. No external error-tracking SaaS for MVP; errors are tracked through structured logs and failure records. Railway Hobby log history is seven days ([Railway logs](https://docs.railway.com/observability/logs)). |
| Tests | Vitest for domain/application rules, adapter/API and PostgreSQL integration tests against local Docker Postgres; React Testing Library for meaningful component behavior; Playwright for critical browser flows ([Vitest](https://vitest.dev/guide/learn/writing-tests)). |
| Visual regression | At UI implementation: deterministic Playwright screenshots at the approved 1448×1086 reference viewport plus responsive viewports, fixed fixture data, stable fonts/assets/time, explicit side-by-side review against each original. After product-owner approval, use Playwright `toHaveScreenshot` baselines in CI; never substitute screenshot for UI ([Playwright](https://playwright.dev/docs/test-snapshots)). |
| Backup/recovery | Neon seven-day point-in-time restore plus scheduled snapshots; encrypted daily logical dumps to private EU R2; restore drills and object reconciliation. Object deletion recovery is separate ([Neon pricing](https://neon.com/pricing)). |
| Secrets/configuration | Runtime environment variables validated at startup, Railway secrets for production, ignored local `.env.local`, checked-in non-secret `.env.example` when implementation begins; configured canonical base URL, auth URL, storage endpoint/bucket, email domain, API endpoints/keys. Never hardcode `debiro.ro` into domain logic. |
| Realtime | No WebSocket/event bus in MVP. Statuses use request/refetch/polling. |

## Comparison method

Correctness/data safety, security, solo maintenance, operational simplicity, low initial cost, portability, then scaling were ranked in that order. Each row gives a credible alternative and why it was or was not selected. Cost is relative unless a verified price is cited in the [cost model](cost-model.md). Migration difficulty refers to switching after an MVP is live.

| Decision / option | Best fit and benefit | Complexity, cost, reliability, security, scaling | Lock-in and migration | Result |
| --- | --- | --- | --- | --- |
| Client: Next.js App Router | Public SSR plus protected app and supplier pages in one process; strong routing and test tooling. | Medium complexity; one server cost; mature accessibility primitives; scales by replicas. Must keep business logic out of framework files. | Medium framework coupling; view/application contracts limit migration cost. | **Selected**. |
| Client: React Router framework mode | Fits app-heavy flows with explicit loader/action model and fewer framework conventions. | Medium complexity and similar hosting cost; viable reliability/security, but marketing SSR and integrated auth/worker examples require more assembly. | Moderate migration from route components; standard React remains portable. | Rejected for this mixed public/app surface. |
| Backend/API: modular monolith + same-origin JSON | Fits one developer, worker sharing rules, supplier portal, and later integrations. | Low operational surface and low fixed cost; testable services; secure central authorization; scale web/worker separately. | Portable Node process and JSON; moderate extraction cost later. | **Selected**. |
| Backend/API: separate API service | Fits many clients/teams or independent scaling requirements. | More deployments, auth/CORS and network failure modes; higher cost and security surface now. | API portable, but migrating to this later is manageable through service boundaries. | Rejected for MVP. |
| Backend/API: server actions only | Fits small web-only forms. | Low initial code, but less explicit HTTP contracts for supplier flows/integrations; risk of rules in UI/framework code. | High migration effort once external clients appear. | Rejected as the sole boundary. |
| API: same-origin JSON + direct server queries | Fits browser interactions while keeping SSR calls inside the application layer. | Zod schemas add modest work; explicit auth/validation/error contracts, simple HTTP caching/tests and future versioned routes. | JSON contracts portable; moderate later extraction. | **Selected**. |
| API: typed RPC throughout | Fits a TypeScript-only client/server with many small calls. | Strong inferred types but extra framework coupling and a less natural future non-TS integration boundary; similar deployment cost. | Moderate-to-high migration for external consumers. | Rejected for the main API boundary. |
| PostgreSQL: Neon Launch | Managed PG, Frankfurt, pooled connections, scale-to-zero, paid restore window without monthly minimum. | Low operations, usage-based; production restore and connection strategy need configuration. Reliable enough for early MVP without claiming a paid SLA. | Standard PG/dumps make migration moderate. | **Selected**. |
| PostgreSQL: Railway template | Fits cheapest same-platform topology and private network. | Lower account count; EU region and backups available, but Railway calls templates **unmanaged**, leaving DB maintenance and recovery to the solo developer ([Railway databases](https://docs.railway.com/databases)). | Standard PG is portable; operational risk higher. | Rejected for production. |
| PostgreSQL: Supabase Pro | Fits a bundled database/auth/storage suite with daily backups. | $25/month baseline and larger included capacity; using only PG wastes bundle, full bundle increases coupling ([Supabase pricing](https://supabase.com/pricing)). | PG portable; bundled auth/storage migrations harder. | Rejected on cost/fit. |
| DB access: Drizzle + reviewed SQL | Fits TypeScript contracts while keeping SQL and migrations visible. | Low runtime overhead, moderate SQL responsibility; explicit tenant filters/RLS and integration tests needed. | Low database lock-in; moderate ORM migration. | **Selected**. |
| DB access: Prisma | Fits teams wanting a high-level relation client and tooling. | Good type safety and migrations; additional generation/runtime conventions and less direct SQL control for RLS-heavy boundaries. | Moderate ORM migration, PG data portable. | Rejected for this SQL-centric design. |
| Auth: Better Auth self-hosted | Fits EU-located identity and sessions in Neon at no auth SaaS fee. | Debiro would own auth migrations, reset/verification email, multi-instance rate limits, CSRF/session hardening, upgrades, abuse response and debugging. Library support helps but does not operate the service. | Lower provider lock-in; identity data portable, session migration still work. | Replaced by ADR-0003 on solo security/operations. |
| Auth: Clerk identity/session only | Fits low-user-count B2B auth without making auth a product differentiator ([Clerk pricing](https://clerk.com/pricing)). | $0 Hobby up to 50k retained users; managed credential/session and abuse controls. No Hobby MFA or custom email templates, fixed seven-day sessions, US identity storage/DPA gate, provider outage dependency; bilingual auth-email webhook/delivery remains debiro's duty and is counted in Resend. | Identity/session migration harder; narrow subject-to-debiro-user mapping limits business coupling. | **Selected by ADR-0003**. |
| Auth: hand-rolled sessions | Fits exceptional identity needs. | Highest security burden despite zero provider fee; poor solo-developer trade-off. | Low vendor lock-in but high maintenance. | Rejected. |
| Tenancy: domain membership + service checks + PG RLS | Fits B2B ownership and supplier capabilities independently of identity vendor. | More policy tests/migration discipline, no extra service cost; two enforcement layers reduce cross-tenant failure risk. | Standard PG data/policies are portable, but policy migration needs care. | **Selected**. |
| Tenancy: application checks only | Fits simpler single-tenant tools. | Cheaper to write initially but one omitted query filter can expose customer data; scales technically but raises audit burden. | Easy to add RLS later only after careful policy rollout. | Rejected for production tenant data. |
| Storage: R2 EU jurisdiction | Fits private S3-style files with guaranteed EU object jurisdiction, free initial allowance and zero egress charge. | Low operations; operations/storage charged after allowances; short-lived bearer URLs require care. Scales without app disk. | S3-compatible path keeps migration moderate. | **Selected**. |
| Storage: Backblaze B2 EU Central | Fits low-cost EU storage and S3 compatibility. | Low operations and 10 GB free; egress conditions and account region setup require care ([B2 pricing](https://www.backblaze.com/cloud-storage/pricing), [regions](https://www.backblaze.com/docs/cloud-storage-data-regions)). | Moderate S3 migration. | Rejected: R2's EU jurisdiction and egress model are simpler. |
| Storage: Railway buckets | Fits one-account convenience and S3-like APIs. | $0.015/GB-month and free bucket egress, but storage is coupled to the runtime account and an explicit EU jurisdiction guarantee was not established during research ([Railway pricing](https://railway.com/pricing)). | Moderate migration. | Rejected for document residency clarity. |
| Upload: direct presigned staging + scan/promotion | Fits supplier files without routing bytes through the web process. | Requires two object states, cleanup and short bearer-URL discipline; bounded web cost and no unscanned downloads. | S3-style flow portable; moderate migration. | **Selected**. |
| Upload: proxy bytes through the web server | Fits tiny attachments needing synchronous inspection. | Simpler browser flow but larger web bandwidth/memory, request timeouts and more sensitive bytes in HTTP path; can scale with dedicated upload tier later. | Moderate migration to direct upload. | Rejected for document flow. |
| Jobs: pg-boss + finite cron worker | Fits low-volume document processing, retries and atomic enqueue without Redis. | Low fixed cost; 10-minute latency and queue monitoring required; scales to a persistent worker later. | PG state is portable; job API migration moderate. | **Selected**. |
| Jobs: Redis/BullMQ or managed queue | Fits sub-minute throughput and independent queue scaling. | Additional service, credentials, backups and cost; strong throughput but more failure modes now. | Medium queue migration. | Rejected until backlog/latency requires it. |
| Scheduler: Railway cron | Fits idempotent daily jobs and finite queue drains. | Low idle cost; five-minute minimum, UTC, skipped overlaps; persist schedule effects in PG. | Low migration effort to another cron or permanent worker. | **Selected**. |
| Scheduler: in-process pg-boss schedules | Fits an always-on worker. | More precise, but keeps DB/worker active and ties recurring work to process liveness. | Low migration, higher idle cost. | Rejected for initial topology. |
| Text/OCR: Poppler then local Tesseract | Fits Romanian/English low volume with private EU processing; paid OCR avoided for text PDFs. | Worker CPU/memory, scanner maintenance and lower accuracy on poor scans; bounded resources and human review required. | Local tools portable; replacement adapter is moderate. | **Selected**. |
| OCR: Google Document AI EU | Fits difficult scans at larger scale or poor local quality. | Managed quality and EU region option; per-page charges and external sensitive-data processing/DPA burden ([Document AI pricing](https://cloud.google.com/products/document-ai/pricing)). | Moderate provider migration. | Rejected for MVP, quality fallback candidate after measured need. |
| AI: OpenAI structured text extraction | Fits typed output from normalized text and human review, with a small model cost. | Usage-based and external processing gate; schema validity does not prove factual accuracy. Bound retries and tokens. | Adapter limits SDK coupling; moderate prompt/model migration. | **Selected**, subject to EU project gate for real data. |
| AI: local model | Fits strict no-external-processing constraints. | High memory/GPU and evaluation burden for a solo developer; no clear low-cost operational win. | Model portable, infrastructure migration significant. | Rejected for MVP. |
| Email: Resend | Fits one sending domain, localized transactional templates, and 1,000/month MVP volume. | 3,000/month and 100/day free; $20 Pro becomes relevant at 10,000/month. Its documented US message/log storage requires transfer/DPA review, despite EU sending. | Provider adapter keeps migration low; replace it if review rejects US storage. | **Selected**, with production legal gate. |
| Email: Amazon SES | Fits high volume and low unit cost. | More AWS setup, sandbox/deliverability operations and separate account; reliable at scale, less simple for MVP. | Low API migration. | Rejected for current volume. |
| Localization: next-intl catalogs | Fits two locales across server/client UI, forms and email with ICU formatting. | Translation review and catalog maintenance are necessary; no separate subscription, and Romanian locked copy stays identifiable. | Message files portable; moderate library migration. | **Selected**. |
| Localization: ad-hoc string maps | Fits a tiny static page. | Low initial setup but pluralization, server context and validation/email consistency become fragile; no vendor cost. | Costly cleanup after copy spreads through components. | Rejected. |
| Hosting: Railway existing Hobby | Fits Node web and finite worker commands in Amsterdam; shared $5 included credits already paid. | Usage-based and simple deploy/metrics/secrets; costs must be measured per project, shared credits cannot be counted twice. | Standard Node deployment keeps migration moderate. | **Selected**. |
| Hosting: Render | Fits web and dedicated workers with managed deployment. | Credible reliability and EU regions, but paid always-on services add a new baseline; pricing was not fully verified from its dynamic calculator. | Moderate migration. | Rejected on incremental cost. |
| Hosting: Fly.io | Fits EU-region small VMs with granular pricing. | Low compute entry price but more VM/network operations for a solo developer ([Fly pricing](https://fly.io/docs/about/pricing/)). | Moderate migration. | Rejected on operations. |
| Environments: local + production + ephemeral previews | Fits visual-first work and a low-cost initial launch. | No permanent staging bill; CI, migrations, fixtures and guarded production deploys must compensate for fewer always-on test environments. | Portable deployment workflow. | **Selected**. |
| Environments: permanent staging | Fits a larger team or integration-heavy releases. | Better long-lived rehearsal but duplicates paid runtime/DB/storage and secrets, adding operating and data-handling burden. | Easy to add when release risk warrants it. | Rejected for MVP. |
| Observability: Railway/Neon + persistent failures | Fits early production without another vendor or document leakage. | Seven-day Railway Hobby logs; alerts and reconciliation must compensate. Metrics/health scale to early traction. | Low migration to later APM. | **Selected**. |
| Observability: Sentry/APM SaaS now | Fits richer issue grouping and traces. | Additional processor, privacy filtering and plan cost/limits; useful after production errors justify it. | Low-to-medium migration. | Rejected for MVP. |
| Testing: Vitest + PG integration + Testing Library + Playwright | Fits deterministic rules, tenant isolation and browser flows without duplicate assertions at every layer. | Local Docker/CI browser setup adds work but no test SaaS fee; coverage targets real failure boundaries. | Common tools, low migration. | **Selected**. |
| Testing: browser E2E only | Fits a short-lived prototype. | Fewer tools initially but slow/flaky feedback and poor isolation of authorization/transaction faults; larger maintenance burden as flows grow. | Adding lower layers later is moderate. | Rejected. |
| Visual QA: deterministic capture + explicit mockup review, then approved CI baselines | Fits canonical mockups where intentional deviations need human judgment. | Stable fixtures/fonts/viewport required; manual review cost initially, later automated pixel checks catch drift. | Playwright images portable; low migration. | **Selected**. |
| Visual QA: auto pixel-diff against mockups immediately | Fits exact renders from the same engine/assets. | Approved image and code render may differ in anti-aliasing/data, producing noisy failures before a faithful baseline exists; low SaaS cost but high triage cost. | Easy to add after approval. | Rejected initially. |
| Recovery: Neon PITR/snapshots + encrypted offsite logical dumps | Fits low-volume production with both provider recovery and independent restore path. | Storage/dump job cost and periodic drills; mitigates provider/configuration mistakes but object deletion still separate. | PG dumps portable; moderate restore operation. | **Selected**. |
| Recovery: provider backups only | Fits noncritical prototypes. | Lowest work, but a single account/provider failure or mistaken configuration can defeat recovery; seven-day window alone may be insufficient. | Portable PG still helps later, but lost history cannot be recreated. | Rejected for production. |
| Secrets: validated env vars + Railway secret store | Fits one production host and local development without another service. | Rotation/access controls require care; no separate fee, and server-only variables must not enter client bundles/logs. | Env contracts portable, low migration. | **Selected**. |
| Secrets: dedicated vault now | Fits many services/operators or complex rotation policy. | Strong central controls but another account, cost and runtime dependency for a solo MVP. | Moderate migration; can add as operational need grows. | Rejected initially. |
| Realtime: request/refetch | Fits asynchronous status updates with minutes-scale jobs. | Simple, low idle cost, accessible and reliable; use bounded polling to avoid load. | Low migration to push later. | **Selected**. |
| Realtime: WebSockets | Fits truly simultaneous edits/live events. | Persistent connections and more auth/operations with no demonstrated MVP need. | Moderate later addition. | Rejected. |

No candidate is assumed to satisfy security merely by offering a feature. The actual implementation must validate auth, tenant isolation, document access, migrations, recovery, and provider contracts before customer use.
